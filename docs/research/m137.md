# M137: offline Dhan order plan and holdings check (M7 prep; pre-registered 2026-10-23, before any code)

Twentieth cycle of the autonomous loop. LOOP step 10 work (live preparation), not a candidate: no variant is added to
the trial count, nothing is adopted, and nothing talks to Dhan.

## Why

M7 (`docs/PLAN.md` §4.7, §12) needs a broker adapter that places the paper book's month-end orders and checks the
broker's holdings against the book every day, with safety rails (§1.6: position caps, kill switch). M130 says the
orders should go in before the open (AMO), since a day's delay costs ~0.6 pts CAGR. M132/cycle 17 say held names
moved to trade-to-trade need care. Today the paper book only writes a readable ticket.

Research this cycle found no new signal with evidence that is not already dead (journal): MF crowding (no Indian
study), network / supply-chain momentum (no emerging-market long-only evidence), absolute + relative momentum (dead,
M72). One candidate was dropped at the information stage: risk-off share in GOLDBEES only while gold is above its
200-day average, cash otherwise. It would act in only 5 of the 45 risk-off month-ends of 2010-23 (6 with a 12-month
return rule), too few to separate from decision-day luck. Not counted.

## What gets built (offline only)

1. `mb data fetch dhan-scrips <live-config>`: Dhan's public scrip master (`api-scrip-master.csv`, no login), stored
   gzipped and unchanged under `data/raw/dhan_scrips/<date>.csv.gz`.
2. `configs/live/dhan_m106.yaml` (strict model `LiveConfig`): the paper config it follows, live capital, order
   fields (exchange segment, CNC, DAY, AMO times for sells and buys), and rails: max order value, max name weight
   after the plan, max buy total as a share of live capital, max orders, kill-switch file, weight tolerance for the
   holdings check.
3. `mb live plan <live-config> [--paper-root P] [--decided D] [--holdings F]`: reads the paper book's pending orders
   (or a past decision with `--decided`), scales shares to the live capital, maps symbols to Dhan security ids (NSE,
   equity, series EQ/BE/...), and writes Dhan v2 `POST /orders` bodies (sells first, then buys; `dhanClientId` left
   for the sender) to `data/live/<name>/plans/<decided>.json` and `.md`. Any rail breach, unknown symbol, kill
   switch, or missing pending orders refuses the whole plan with the reasons. With `--holdings` (a saved Dhan
   `GET /holdings` response), full exits sell the broker's quantity.
4. `mb live reconcile <live-config> --holdings F [--paper-root P]`: names held on one side only, and names whose
   weight differs by more than the tolerance; exit code 1 on any mismatch.

No order is sent, no token is read. Sending stays M7 proper and needs the user's go-ahead (capital, static IP,
client id).

## Checks (pass = the tool is right; there is no return bar)

- Unit tests: payload fields and order (sells before buys), scaling and whole shares, each rail refuses, kill switch,
  unknown symbol, `--holdings` exit quantities, reconcile finds one-sided names and weight gaps and passes a match.
- End to end (read-only on `~/projects/multibagger-v2`): a plan for the voladj book's 2026-09-30 decision
  (`--decided`) maps all its symbols to security ids and passes the rails at ₹10 lakh; a reconcile of its current
  book against a holdings file written from that book passes.
- `uv run pytest` passes.

## Results (2026-10-23)

Built as registered: `src/mb/sources/dhan_scrips.py`, `src/mb/live/broker.py`, `configs/live/dhan_m106.yaml`,
CLI `mb data fetch dhan-scrips`, `mb live plan`, `mb live reconcile`. Scrip master fetched once
(`data/raw/dhan_scrips/2026-10-23.csv.gz`, 3.0 MB; 10,005 NSE cash rows, 2,732 in series EQ).

Choices written into the config (the user can change them before M7): sells MARKET into the pre-open auction
(`PRE_OPEN`), buys MARKET at the open (`OPEN`) after the sells free the cash; no limit prices by default, because a
limit outside a stock's 2-20% band is rejected. LIMIT with a buffer and tick rounding is supported. Rails: ₹6.5 lakh
per order (the largest normal order is the risk-off switch into GOLDBEES), 12% per name, GOLDBEES 65%, buys ≤ capital,
60 orders, kill switch `data/live/STOP`, 2-point weight tolerance for the holdings check.

Checks:
- Unit tests `tests/test_m137_live_plan.py`: 13 passed (payload fields, sells first, scaling, tick rounding, every
  rail, kill switch, holdings-based exits, reconcile, CLI from pending orders). Suite: 345 passed, 9 skipped.
- End to end, read-only on `~/projects/multibagger-v2` (temporary live config pointing at the voladj book): the
  2026-09-30 decision maps all 30 symbols to one security id each and passes the rails at ₹10 lakh (buys ₹9.81 lakh).
  At ₹1 lakh three names (CPPLUS, KENNAMET, SANSERA) round to 0 shares and are skipped with a note, so whole-share
  rounding sets a floor on live capital: about ₹2.5 lakh for M106's 25 names (M135 tranches saw a 1.3% gap there).
- Reconcile of the voladj book as of 2026-10-22 against a holdings file written from it: match (30 names); the same
  at twice the size plus one share: match (weights are compared, not counts).

Verdict: pass (tooling). Nothing sent, no token read, running books untouched. Variants for adoption: unchanged
(~1,014). One deviation: refusals and mismatches exit with code 2 (the CLI's error code), not 1. For M7 proper: the user's capital, Dhan client id, a static IP for order APIs (Dhan requires it), then a
sender that posts these bodies and saves the replies, and a daily `GET /holdings` dump into `mb live reconcile`.
